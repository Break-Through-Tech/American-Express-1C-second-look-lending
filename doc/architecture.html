Architecture & model design

Second-Look Lending

A web app that predicts each applicant's probability of default (PD), turns it into an approve / deny decision that maximizes profit, and gives thin-file applicants (no credit history) a fair second look.

Backend: Python · FastAPI · pandas · scikit-learn · LightGBM · Optuna. Frontend: React (Vite) · Recharts. Data: synthetic lending dataset, 1,000,000 train loans (weeks 0–91) and 200,000 out-of-time test loans (weeks 92–107).

Honest reading

Calibration does most of the work: "Calibrated PD < 20%" is the most profitable policy on test. The per-segment thresholds are tuned on only 6 weeks, so they are noisier and here overshoot past zero gap. The gap penalty decides how much profit to trade for fairness, and can be changed in the Policy lab.

The React app talks to one FastAPI server. Training runs in a background thread so the UI stays responsive and can show live progress. Everything the models produce is saved to backend/artifacts/.

3. Model pipeline

From eight raw tables to a decision. The two coloured paths show how the same PD is used by the baseline policy (gray) and by the second-look policy (aqua).

Only the train file is used to fit and tune. Weeks 80–85 tune the model; weeks 86–91, which the model never saw, tune the policy. The test answer key is used once, to score.

Optuna (TPE sampler) runs on a 25% stratified sample with one declared metric, model-validation AUC (weeks 80–85). scale_pos_weight is not tuned: it barely changes AUC but makes every PD too high, which breaks the 20% decision rule.

Why not stratified K-fold (slide 13)? The test set is later in time and risk drifts, so a random K-fold would mix future weeks into training and over-state performance. A time-ordered holdout copies the real out-of-time test.

6. Decision policy

Cost model → approval rule

Repaid loan +$2,000 · defaulted loan −$8,000 · denied applicant $0

Expected value of approving = (1 − PD) × 2,000 − PD × 8,000
Positive only when PD < 2,000 / (2,000 + 8,000) = 20%

Inclusion gap

gap = approval rate of established good payers − approval rate of thin-file good payers (percentage points)

Inclusive Profit Score

score = profit − penalty × |gap| × (applicants / 100,000)
only if default rate among approved loans ≤ ceiling

Defaults: penalty $100,000 per gap point per 100k applicants, ceiling 12%.

Why the baseline is unfair

The thin-file default rate falls from about 33% in week 0 to about 19% by week 91, while established stays near 16%. Test weeks come later, so on test the model predicts 25.9% PD for thin-file applicants whose real default rate is 17.8%. A flat 20% cut-off then denies many thin-file applicants who would repay.

The second look

  1. Segment-aware calibration. Fit Platt scaling (or isotonic regression) separately for thin-file and established on the policy-validation weeks 86–91, which the model never saw.
  2. Drift correction. On weeks 0–85, fit a straight line to each segment's weekly default rate in log-odds (thin-file ≈ −0.0084 per week, established ≈ 0). Move each calibrated PD along that line from the policy-validation midpoint to the applicant's own week. Thin-file mean PD on test becomes 18.0% (actual 17.8%).
  3. Segment-aware thresholds. Try every pair of thresholds from 5% to 50% in 0.5% steps on weeks 86–91, and keep the pair with the best Inclusive Profit Score. Result for the best model: established < 17.5%, thin-file < 24.5%.

8. How to run

# Backend
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
scripts/fix_lightgbm_macos.sh                 # macOS without Homebrew libomp only
export SLL_DATA_DIR="/path/to/synth_home_credit"   # only if it is not in data/synth_home_credit
.venv/bin/uvicorn app.main:app --port 8000 --reload

# Frontend (second terminal)
cd frontend
npm install
npm run dev                                   # http://localhost:5173

# Or build the UI once and open http://localhost:8000
npm run build

# Train without the UI
.venv/bin/python -m app.cli --model lightgbm --trials 20

# Regenerate the data dictionary after changing features.py
.venv/bin/python scripts/make_data_dictionary.py

# Rebuild and execute the notebook from its source (notebooks/build_notebook.py)
cd ../notebooks && ../backend/.venv/bin/python build_notebook.py --run

The first request builds the feature tables (about 20 seconds) and caches them in backend/artifacts/features/.
