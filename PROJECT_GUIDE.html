Second-Look Lending

Predict each applicant's probability of default, turn it into an approve / deny decision that makes money, and give applicants with little credit history a fair second look.

This guide is for anyone joining the project: what it does, how it is built, how to run it, how to use every page, and where to start reading the code. A Markdown copy for GitHub is in PROJECT_GUIDE.md.

1. What this project is

A lender has a cost model: a repaid loan earns +$2,000, a default loses −$8,000, a denied applicant is $0. So approving only pays off when the probability of default (PD) is below 2,000 / (2,000 + 8,000) = 20%.

The catch is thin-file applicants: people with no credit-bureau history (30% of applicants). The model knows less about them, and in this data their risk falls over time, so a model trained on older weeks thinks they are riskier than they are. A flat 20% rule then turns away many who would have repaid. The project measures that unfairness (the inclusion gap) and fixes it without losing profit.

The dataset is synthetic — it mimics a real credit bureau's tables but contains no real people.

Every model earns more and becomes fairer with the second-look policy. Of thin-file applicants who repaid, 80.6% are approved instead of 41.2%. Most of the gain comes from calibration: thin-file PDs go from 25.9% (raw) to 18.0%, against a real default rate of 17.8%.

These numbers are for Second Look deciding every application. In the app's pipeline Second Look only looks again at the primary model's declines, which gives $147.7M → $154.0M and a gap of 36.9 → −2.5 pts.

Thin-file flag: an applicant with zero rows in credit_bureau_a_1. Those people also miss static_cb_0 and credit_bureau_a_2, so every bureau feature is empty for them.

Lending always predicts the future from the past, so we split by week, never at random. Each window has one job, so nothing is judged on data it was tuned on.

5. How training works

Three algorithms, from simplest to strongest. Each one outputs a PD between 0 and 1.

ModelIdea in one line"Epochs"?
Logistic RegressionOne weight per feature, add them up, squash into a probability.max_iter: each solver iteration is one pass over all loans (stopped after 67).
Random ForestHundreds of independent decision trees on random samples, averaged.None — every tree is built once.
LightGBMTrees built one after another, each fixing the mistakes left by the previous ones.Boosting rounds: one tree per round, stopped early by validation AUC.

6. The decision policy

flowchart LR PD("Raw PD
from the model"):::ml subgraph OLD["Baseline (old way)"] direction LR B{"PD < 20%?"}:::decision A0(["Approve"]):::good R0(["Deny · many good

~0.008 log-odds / week"):::ml T{"Segment threshold
est 17.5% · thin 24.5%"}:::decision A(["Approve"]):::good R(["Deny"]):::bad C --> DR --> T T -->|below| A T -->|above| R end PD --> B PD --> C
  • Inclusion gap = among applicants who actually repaid, approval rate of established minus thin-file.
  • Inclusive Profit Score = profit − penalty × |gap|, counted only if the default rate of approved loans stays under 12%. Penalty: $100,000 per gap point per 100k applicants.
  • Thresholds are searched on weeks 86–91 (every pair from 5% to 50%) and the best score wins.

The decision pipeline: primary → Second Look → a person

In the app the two run one after the other. The primary model decides first with one 20% cut-off. Only its declines go to Second Look — automatically, or when a business user sends them (Work queue → Manual). Second Look declines that are close to the cut-off wait for a person.

  • Review band (2 points by default) decides how close counts as borderline — about 260 cases a week.
  • A reviewer can approve against the model (an override) only with a written reason. Every step, who did it and the terms they changed go into the audit trail.
  • The primary and second-look models are chosen by the tech team on Compare models; until then both use the run with the best validation AUC. Settings live in workflow_settings.json and model_roles.json.
  • Online applications enter here too. applications.py starts from a typical recent applicant in the same credit-history group and puts the applicant's answers on top, so the models get a full feature row. Name and email stay in the local workflow.db and never reach the models.

7. Setup guide

You need: Python 3.9+, Node.js 18+, git, and the dataset folder synth_home_credit (containing csv_files/ and solution.csv). No GPU, no accounts. Python comes from python.org (on Windows tick Add python.exe to PATH).

Install Node.js (once)

Node.js runs the web app's build tools; npm comes with it. Install the LTS version (18 or newer).

SystemEasiest wayOr from the command line
macOSDownload the macOS installer (.pkg) from nodejs.org and run itbrew install node (needs Homebrew)
WindowsDownload the Windows installer (.msi) from nodejs.org and run it, keeping Add to PATH tickedwinget install OpenJS.NodeJS.LTS
LinuxYour package manager (e.g. sudo apt install nodejs npm), if it offers 18+nvm: nvm install --lts

Then open a new Terminal / Command Prompt (so it finds Node) and check:

node --version    # v18 or newer
npm --version

No admin rights on your Mac? Download the macOS binary (.tar.gz) from nodejs.org, unpack it into your home folder (for example ~/.local/node), and add export PATH="$HOME/.local/node/bin:$PATH" to ~/.zshrc.

Quick start. After steps 1 and 2 below, one script does the rest. macOS / Linux: ./setup.sh once, then ./start.sh. Windows: setup.bat once, then start.bat (double-click or Command Prompt). Open http://localhost:8000. Add --dev to the start script for a live-reloading UI on port 5173. The scripts check Python and Node, install everything, build the UI, check the dataset and are safe to re-run. Windows needs the Microsoft Visual C++ Redistributable (x64) for LightGBM.

Prefer to do it by hand? The manual steps:

  1. Get the code 
    git clone https://github.com/Break-Through-Tech/American-Express-1C-second-look-lending.git
cd American-Express-1C-second-look-lending
  2. Add the dataset

    Put (or unzip) it at data/synth_home_credit/, so that data/synth_home_credit/csv_files/ exists. The app reads it from there; there is nothing to configure. The folder is git-ignored, so the data is never committed.

  3. Install and start the backend 
    cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
scripts/fix_lightgbm_macos.sh        # macOS only, if Homebrew's libomp is missing
.venv/bin/uvicorn app.main:app --port 8000 --reload

    Check it: http://localhost:8000/api/health should say "data_found": true. Interactive API docs: /docs.

  4. Install and start the frontend (second terminal) 
    cd frontend
npm install
npm run dev                          # open http://localhost:5173

    Or build once with npm run build and use http://localhost:8000 — FastAPI serves the built app.

  5. Train your first models

    On the Train page, train Logistic Regression, then Random Forest, then LightGBM. The first request builds the feature tables (about 20 seconds) and caches them. Each model takes 5–20 seconds; LightGBM with 20 Optuna trials about a minute.

Prefer the terminal? .venv/bin/python -m app.cli --model lightgbm --trials 20 trains a run without the UI. The notebook notebooks/second_look_lending.ipynb runs the whole project on free Colab.

8. How to use the app

The app has three workspaces — pick one on the home page or with the switcher at the top. Help (top right) has the project overview, how-to guides, a glossary and FAQs.

Applicant

/apply · /apply/status · /apply/1000005

For people applying for a loan. A five-step form (loan, about you, income & work, credit history, review & submit) gives an instant decision and an application number; Check your status finds it again. The decision comes first, then plain-language reasons (what helped, what held it back), a loan-amount slider for what-if, and next steps. No risk scores or jargon. "Approved through Second Look" appears when the second look made the difference.

Business

/business/pipeline · /business · /business/statistics · /business/policy

Work queue (opens first): process a week, send declines to Second Look (automatic or manual), open a borderline case, change terms, re-score and decide; the Online applications tab lists every application submitted on Apply with its decision. Dashboard: profit, approval rate, default rate and inclusion gap, primary model only vs with Second Look. Statistics: how many the primary model approved or declined, how many went through Second Look and how many wait for a person, with charts. Policy lab: Preview a policy change safely; Publish makes it live.

Tech team

/tech · /tech/insights · /tech/train · /tech/models

Data overview: the data flow (8 raw tables → feature table → split by week) and the training data itself — browse every raw table and the feature table, filter, and follow one loan across tables. Insights: how features are built and how models work. Train models: settings with ⓘ tooltips and a live training view. Compare models: compare on validation, then Set as primary or Set as second look.

Help

/help

Project overview, how the workspaces connect, step-by-step guides for each role, how decisions are made, a glossary, FAQs and links to this guide and the API docs.

Golden rule: make every choice (model, settings, policy) on validation. Look at the test numbers once, at the end. Picking by test score quietly turns the test set into training data.

9. Code walkthrough

The backend is plain Python functions with one-line comments; the frontend is plain React with one file per page. Read in this order:

  1. backend/app/config.py — paths, the cost model, the week split. 30 lines.
  2. backend/app/features.py — how 8 tables become 53 features. One small function per table.
  3. backend/app/models.py — PDModel wraps preprocessing and model for all three algorithms; fit() and predict_pd() are the core.
  4. backend/app/training.py — train() ties it together: split, tune, fit, score, save.
  5. backend/app/policy.py — the money maths: calibration, drift, profit, gap, threshold search.
  6. backend/app/main.py — every API route in one file; each route is a few lines.
  7. frontend/src/api.js, then App.jsx (routes) and components/Layout.jsx (header and workspaces), then pages/ — one folder per workspace: applicant/, business/, tech/.

Common changes

Add a feature

Add a column in features.py (inside the table's aggregation function, or in add_derived_features). Delete backend/artifacts/features/ or call POST /api/features/build, retrain, then run scripts/make_data_dictionary.py.

Add a model

Add it to MODEL_NAMES and DEFAULT_PARAMS in models.py, build it in build_model(), give it a search space in suggest_params() and help text in param_help.py. The UI picks it up automatically.

12. Glossary

PD
Probability of default: the model's estimate that a loan won't be repaid.
Thin-file
An applicant with no credit-bureau history.
AUC
How well the model ranks people: 0.5 is guessing, 1 is perfect.
LogLoss / Brier
How far PDs are from what happened. Lower is better.
Calibration
Whether a PD of 20% really means 20 in 100 default.
Drift
Data changing over time; here thin-file risk falls week by week.
Early stopping
Stop adding trees once validation stops improving.
Epoch
A full pass over the data. Not used by these models; see section 5.
Inclusion gap
Approval rate among repayers: established minus thin-file.
Out-of-time test
Later weeks the model never trained on, scored once at the end.
